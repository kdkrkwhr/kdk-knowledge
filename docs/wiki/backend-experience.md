# 백엔드 설계와 운영 경험

**출처 구분:** 본인이 제공하고 공개를 확인한 경력 설명입니다. 회사의 공식 경력 증명이나 공개 코드의 독립 검증 결과를 뜻하지 않습니다. 비공개 이력서 원본·내부 코드·운영 데이터는 포함하지 않습니다. **기준일: 2026-11-09.**

## 경험의 범위

Java·Spring 기반 API와 데이터 접근 계층을 중심으로, 서비스 전환과 리뷰·콘텐츠, 결제·쿠폰, 알림 및 IoT 기능을 다뤘습니다. 서로 다른 도메인에서도 요청이 들어와 데이터가 바뀌고 외부에 결과가 전달되는 전체 흐름을 이해하는 일이 중요했습니다.

이 문서는 특정 회사의 내부 구성을 재현하기보다, 담당했던 업무와 그 경험을 설명할 때 확인하는 설계 질문을 연결합니다. 아래 점검 항목을 모든 프로젝트에 동일하게 적용했다는 뜻은 아닙니다.

## 여기어때에서의 약 4년: 기능 개발과 서비스 운영

여기어때컴퍼니에서 2022년 5월부터 2026년 4월까지 근무하며 리뷰·콘텐츠, 사용자 알림과 상담 기능을 다뤘습니다. 이 기간의 경험에는 API 구현뿐 아니라 Kafka, MSA와 안정적인 서비스 운영을 위한 인프라 작업도 포함됩니다.

서비스가 동작하는 코드를 만드는 것에서 출발해, 여러 서비스가 연결된 상태에서 데이터를 처리하고 변경을 배포·관찰·복구하는 일까지 시야를 넓혔습니다. 아래는 그 경험에서 배운 점을 일반화해 정리한 내용입니다. 특정 서비스의 내부 구성도나 운영 절차를 공개하는 것은 아닙니다.

## Kafka: 메시지 전달과 업무 처리의 차이

Kafka를 사용하는 서비스 환경을 경험하며 비동기 처리의 장점과 함께, 메시지가 전달된 상태와 업무 처리가 완료된 상태를 구분하는 관점을 배웠습니다. 생산자와 소비자의 실행 시점이 분리되면 처리 속도, 실패와 재시도를 함께 생각해야 합니다.

관련 경험을 돌아볼 때는 다음 질문을 나누어 봅니다.

- 소비자가 처리에 실패하면 어디까지 완료된 것으로 판단하는가?
- 같은 메시지를 다시 처리해도 업무 결과가 중복되지 않는가?
- 처리 순서가 중요한 데이터는 무엇이며 그 범위는 어디까지인가?
- 소비 속도가 떨어졌을 때 지연이 사용자 기능에 어떻게 영향을 주는가?
- 소비자 재시작이나 재분배 상황을 정상 처리와 어떻게 구분해 확인하는가?

메시징을 도입했다는 사실만으로 전달과 처리의 모든 조건이 보장되지는 않습니다. 메시지 처리 경계, 상태 저장과 재시도 후 결과를 함께 설명하는 것이 중요하다고 배웠습니다. 이 항목은 경험에서 정리한 검토 관점이며, 특정 Kafka 설정이나 모든 상황의 검증 완료를 주장하지 않습니다.

## MSA: 서비스 경계와 변경 영향 이해하기

MSA 환경과 도메인 경계 분리를 경험하면서, 서비스를 나누는 작업은 코드나 저장소를 분리하는 것에 그치지 않는다는 점을 배웠습니다. 각 기능의 책임, 데이터의 기준과 서비스 사이의 요청·응답 계약을 함께 이해해야 합니다.

한 서비스의 변경이 다른 호출자에게 영향을 줄 수 있고, 연결된 서비스가 지연되거나 실패하면 전체 기능의 동작도 달라집니다. 따라서 개별 API의 정상 동작뿐 아니라 서비스 간 경계에서 생길 수 있는 문제를 생각하게 됐습니다.

- 어느 서비스가 데이터와 상태 변경의 책임을 갖는가?
- 동기 호출과 비동기 처리를 어떤 문제에 적용하는가?
- 한쪽이 먼저 배포돼도 기존 호출자가 기대하는 계약을 유지할 수 있는가?
- 일부 처리만 완료된 상황을 어떤 상태로 설명할 수 있는가?
- 문제가 생겼을 때 어느 서비스의 어느 단계부터 확인해야 하는가?

이런 관점은 리뷰·콘텐츠 API의 도메인 경계와 사용자 알림의 이벤트 처리를 설명할 때도 연결됩니다. 실제 회사의 서비스 수, 통신 경로와 데이터 분할 구조는 공개하지 않습니다.

## 안정적인 운영을 위한 인프라와 배포 작업

여기어때에서 기능 개발과 함께 부하 테스트, 병목 분석, 모니터링·로깅, 배포 파이프라인과 롤백 체계를 다뤘습니다. 인프라 작업도 애플리케이션과 별개의 영역으로만 보지 않고, 서비스가 실행되고 변경되는 조건을 이해하는 과정으로 경험했습니다.

배포가 끝났다는 사실과 서비스가 정상이라는 판단은 구분해야 합니다. 변경 후 무엇을 관찰할지, 문제가 발생하면 어떤 상태로 되돌릴지까지 생각하는 것이 운영의 일부라고 배웠습니다.

- **부하와 병목:** 테스트의 입력·환경·부하 조건을 명확히 하고 어떤 구간이 제한되는지 확인합니다.
- **모니터링과 로그:** 사용자에게 나타난 현상과 실제 처리 단계를 연결해 볼 정보를 정리합니다.
- **배포와 검증:** 변경 내용이 의도한 환경에 반영됐는지와 기능이 유지되는지를 구분해 확인합니다.
- **롤백과 복구:** 실패 시 되돌릴 범위와 데이터·연동 기능에 미칠 영향을 함께 생각합니다.

운영 경험을 설명할 때는 담당한 작업과 조직 전체의 인프라 운영을 구분합니다. 이 문서는 전체 플랫폼 인프라를 단독 설계·운영했다는 뜻이 아니며, 내부 자원 규모나 배포·접속 설정은 포함하지 않습니다.

## 기존 계약을 유지하는 서비스 전환

기존 백엔드 기능을 다른 언어와 프레임워크로 옮기는 작업에서 인증, 요청·응답 계약과 데이터 접근 계층을 다뤘습니다. 전환에서는 구현 언어가 달라져도 기존 호출자가 기대하는 동작이 유지되는지가 중요합니다.

업무를 설명할 때는 외부에 유지해야 할 인터페이스와 새 환경에서 바꿀 내부 구현을 나눕니다. API가 응답한다는 것만으로 전환이 완료되는 것은 아니므로, 비교할 입력과 결과의 기준을 함께 정리합니다.

- 요청 파라미터와 필수·선택 값의 의미
- 응답 구조와 오류 처리 방식
- 인증 이후 데이터에 접근하는 흐름
- 데이터 조회·변경 결과의 비교 기준
- 배포 이후 확인할 항목과 복구 방법

[AI 경험](ai-experience.md)에서 다루는 검색 전환 역시 같은 관점으로 살펴봅니다. 기존 동작과의 비교와 새 기능의 품질 평가는 구분해서 설명합니다.

## 리뷰·콘텐츠 API와 캐시

리뷰·콘텐츠 API를 개발하며 조회 기능과 캐시 관리, 데이터 정합성을 함께 다뤘습니다. 캐시는 조회를 빠르게 하는 수단이지만, 원본이 바뀌었을 때 어떤 데이터를 보여줄지도 결정해야 합니다.

관련 경험을 정리할 때는 캐시 대상, 갱신·무효화 시점, 갱신 실패 시 사용자에게 보이는 결과를 나눠 봅니다. 성능 수치만으로 선택을 설명하기보다 데이터가 변경되는 빈도와 허용할 수 있는 지연을 함께 생각합니다.

데이터 접근 계층에서는 어떤 조회가 반복되는지, 필요한 범위보다 많은 데이터를 읽고 있지는 않은지와 같은 질문으로 병목을 살펴봅니다. 공개 문서에는 실제 서비스의 데이터 규모, 내부 쿼리나 운영 구성을 싣지 않습니다.

## 사용자 알림과 이벤트 처리

사용자 알림 기능에서 이벤트 처리와 상태 관리, 동시성 제어를 경험했습니다. Outbox 패턴과 분산 잠금 등은 이런 업무를 설명할 때 연결할 수 있는 기술입니다. 패턴의 이름보다 해결하려는 문제와 남는 제약을 먼저 구분합니다.

- 이벤트 누락: 데이터 변경과 후속 처리 사이에 무엇이 보장돼야 하는가?
- 중복 요청: 같은 작업이 다시 실행될 때 결과가 중복되지 않는가?
- 동시 변경: 여러 요청이 같은 상태를 바꿀 때 지켜야 할 조건은 무엇인가?
- 실패와 재시도: 어느 단계까지 완료됐고 어디부터 다시 시작해야 하는가?

이 질문들은 각각 다른 검증이 필요합니다. 하나의 락이나 메시징 도구가 모든 문제를 해결한다고 설명하지 않고, 실제 담당한 범위와 검증한 동작을 구분합니다.

## 결제·쿠폰과 외부 시스템 연동

결제·쿠폰 API 개발과 운영에서는 발급·사용 처리 및 결제 연계를 다뤘습니다. 외부 시스템과 연결되는 문제를 분석할 때는 우리 시스템의 처리 결과와 상대 시스템의 응답을 함께 확인해야 합니다.

경험을 문서로 남길 때는 요청, 응답, 결과 저장 순서를 구분하고, 실패한 단계와 확인된 사실을 정리합니다. 성공 응답을 받는 경로뿐 아니라 실패 이후 상태를 어떻게 해석하는지도 서비스 설명의 일부입니다.

실제 거래나 계약 정보는 제외하고, 입력 조건·상태 변화·오류 처리라는 일반화 가능한 관점으로 경험을 연결합니다.

## IoT와 실시간 관제

장비·사용자 관리 API, 측정 데이터 수집과 모니터링, 앱 연동 및 통계·알림 기능을 경험했습니다. 영상 기반 교통정보 처리와 실시간 위치 관제 개발에도 참여했습니다.

이 경험에서는 수집되는 데이터가 관리 API, 조회 화면과 모니터링 기능으로 어떻게 이어지는지 살펴봤습니다. 시스템을 설명할 때 수집과 저장, 조회와 표현의 역할을 나누면 담당 범위를 분명하게 전달할 수 있습니다.

개별 장비의 정보나 실제 위치 데이터 대신, 데이터를 다루는 기능의 책임과 운영 관점을 중심으로 기록합니다.

## 구현 이후의 검증과 운영

부하 테스트와 병목 분석, 모니터링·로깅, 배포·롤백을 함께 다뤘습니다. 기능 구현 이후에도 실패·재시도와 운영 중 확인할 정보를 고려합니다.

테스트 결과를 기록할 때는 환경, 입력과 부하 조건, 관찰한 결과를 함께 남기려고 합니다. 특정 조건에서 얻은 수치를 서비스 전체의 안정성이나 모든 환경의 성능으로 일반화하지 않습니다.

[멘토링](mentoring-experience.md)에서도 같은 관점으로 구현한 기능, 선택 이유, 확인한 결과와 남은 문제를 구분해 설명하도록 피드백했습니다.
