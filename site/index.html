    00 / ORIENTATION

    경험을 근거와 함께 남기는 곳

    이 위키는 김동기의 프로젝트, 맡은 역할, 기술 선택과 배움, 그 경험에서 정리한 개발 기준을 연결하기 위한 개인 지식 허브입니다. 지금은 공개된 두 저장소를 출발점으로 삼습니다.

    각 설명은 확인한 공개 원본으로 돌아갈 수 있어야 합니다. 위키 문장은 LLM이 공개 자료를 읽고 정리한 해설이며, 자동 코드 분석 결과가 아닙니다. 아래에 없는 경력이나 성과를 추측해 채우지 않습니다.

    구조 지도에서 현재의 연결과 출처를 함께 볼 수 있습니다.

    01 / PROJECTS

    공개 프로젝트

    노트버디 · Notebook Pets

    공개 README는 그림이나 사진으로 AI 친구를 만들고, 돌봄과 대화, 산책과 모험으로 함께 성장하는 프로젝트라고 설명합니다. 이 허브에서는 프로젝트의 범위와 구현을 탐색하는 출발점으로 연결합니다. 개인이 맡은 구체적 역할이나 성과는 아직 별도 근거가 없어 적지 않았습니다. README 원본 ↗

    기능과 코드의 연결은 기존 프로젝트 위키에서 읽을 수 있습니다. 그 위키는 LLM 해설과 Graphify 자동 문서를 구분합니다. 위키 원본 ↗

    02 / CRITERIA

    개발 기준은 여러 영역 중 하나

    Engineering Standards는 프로젝트에서 필요한 공통 원칙과 언어·프레임워크별 프로필을 선택해 적용하는 공개 자료입니다. 특정 언어나 구조를 모든 작업에 강제하지 않는다고 명시합니다.

    공통 원칙에는 요구와 수용 조건의 확인, 책임의 경계, 오류의 구분, 명명, 테스트, 변경 범위와 검증 기록이 있습니다. 이것은 참조할 기준 자료이며, 김동기의 모든 프로젝트에 이미 적용됐다는 뜻은 아닙니다. 실제 적용이나 예외는 해당 프로젝트의 결정 근거와 함께 기록해야 합니다. 공통 원칙 원본 ↗

    03 / CAREER

    경력과 역할

    공개 가능한 역할·기간·성과와 그 근거가 아직 등록되지 않았습니다. 회사 내부 정보나 기억에 의존한 내용을 이 공개 위키에 넣지 않습니다.

    추가할 때는 경력 템플릿에 공개 가능한 범위와 확인 가능한 원본을 먼저 적습니다.

    04 / TECHNOLOGY

    기술과 선택 이유

    기술을 사용한 프로젝트, 선택 이유, 대안, 배움의 근거가 아직 등록되지 않았습니다. 언어와 프레임워크를 미리 한정하지 않습니다.

    사용 사실과 선택 이유를 구분해 기술·결정·학습 템플릿으로 추가합니다.

    05 / MAINTENANCE

    기록을 추가하는 법

    1. 원본의 공개 여부를 확인하고, URL과 커밋 또는 문서 버전을 고정합니다.
    2. 사실, 해석, 개인의 배움을 구분해 작성하고 각 관계에 근거를 연결합니다.
    3. 공개해도 되는 내용인지 사람이 검토합니다. 비공개 자료는 공개 저장소에 올리지 않습니다.
    4. python3 scripts/validate.py와 python3 -m unittest discover -s tests -v를 실행한 뒤 변경을 배포합니다.

    참고 소스의 새 버전이 나오면 이전 SHA를 자동으로 바꾸지 않고, 차이를 읽고 해설을 다시 대조합니다. 관리 안내 ↗
